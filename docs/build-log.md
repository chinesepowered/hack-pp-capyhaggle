# Build log

Dated notes of surprises, walls and workarounds while building Capy vs Capy. All times are from the cloud build
session on Tuesday 2026-11-10.

## PayPal

- **The sandbox flow worked end to end by script before any app code existed.** Order with intent AUTHORIZE, buyer
  approval, authorize, capture, payout: all green on the first pass with the provided sandbox app. That smoke run
  became the first section of `paypal-plan.md`.
- **Buyer approval can be automated in headless Chromium.** PayPal's sandbox login is two steps (`#email`,
  `#btnNext`, then `#password`, `#btnLogin`) and the pay button is `[data-testid="submit-button-initial"]`. With an
  existing session the login step is skipped, so the script races "login form" against "pay button". This is
  `scripts/lib/approve.ts`, used by `pnpm seed` and the recorders.
- **Agent Toolkit `create_order` cannot place a hold.** In `@paypal/agent-toolkit` 1.11.0 the order tool hardcodes
  `intent: "CAPTURE"`. Our whole product is a hold, so the order is created by our own tool
  (`create_held_order`, on the server SDK). The toolkit is used where it fits: `get_order` (the seller's agent
  verifies the hold itself) and `create_refund`.
- **The Agent Toolkit returns bodies only, no headers.** The "Under the hood" drawer needs `PayPal-Debug-Id` for every
  call. The toolkit uses its own axios instance, and patching axios would hit the dual ESM and CommonJS copies. We
  subscribe to Node's `diagnostics_channel` (`http.client.request.start` and `http.client.response.finish`) and tag
  only the requests that start inside a toolkit call. This also revealed that the toolkit fetches its own OAuth token,
  which the drawer now shows honestly.
- **The Agent Toolkit only sends `PayPal-Request-Id` when the context carries `request_id`.** Reads share one toolkit
  instance; a refund gets its own instance with the deal-derived request id.
- **The server SDK does not cover Payouts or Webhooks.** Those are plain REST with the same token helper. The SDK's
  `oAuthTokenProvider` hook lets the SDK and the REST helper share one cached token.
- **Payout timing.** A payout batch goes PENDING, PROCESSING, SUCCESS in roughly 5 to 20 seconds in the sandbox, and
  the item status lags the batch status. The paid screen polls `GET /v1/payments/payouts/{id}` until the item is
  SUCCESS. The drawer collapses those identical polls into one row with a count.
- **Fees are real numbers, so the marketplace fee had to be chosen against them.** On an $82.00 capture the sandbox
  charged a $3.35 PayPal fee, and the payout cost $0.25. The fee shown at Accept is 5% plus $0.50 ($4.60 on $82), which
  covers both.
- **Order ids are not always the familiar 17 characters.** One sandbox order id came back as a 17 digit number. We
  never validate id shapes ourselves.
- **Unknown outcomes.** A write that gets no answer is not a failure. Each write has a settle step: repeat with the
  same `PayPal-Request-Id` (create order), re-read the order (authorize), re-read the authorization (capture, void), or
  repeat with the same `sender_batch_id` (payout). These are covered by tests with a faked transport because the
  sandbox never dropped a connection for us. The duplicate `sender_batch_id` branch is written from PayPal's docs and
  was not hit against the real sandbox.
- **Webhooks could not be exercised from the cloud session** (no public URL). The handler verifies the signature
  through `POST /v1/notifications/verify-webhook-signature` with the raw body spliced in byte for byte, is idempotent
  by event id, and only uses an event as a trigger to re-read PayPal. See `docs/needs-user.md`.
- **Replay mode and reauthorization.** The recorded authorization is a few days old the moment anyone replays it, so
  the "past the 3 day honor period, reauthorize first" branch would fire against a recording that has no such call.
  Replay skips that branch; Live keeps it.

## APIMatic Context Plugin

- **The installer was blocked.** `npx skills add <github url>` executes code fetched from an external repository and
  the cloud sandbox refused it. We used the fallback from the brief: clone `context-plugins/plugin-marketplace`, read
  `plugins/paypal`, and copy the nine `typescript-*` skills into `.claude/skills/` (commit `7cbdf85`).
- **The plugin documents a different package than the one on npm.** Its lookup layer describes `paypal`
  (`PaypalClient`, version 2.29.0, installed from git and built from source). The brief pins
  `@paypal/paypal-server-sdk` 2.5.x, which is also generated by APIMatic but has a different surface
  (`Client`, controllers, `ApiResponse`, `ApiError`). We kept the plugin's method and pointed it at the installed
  package: no SDK fact from memory, every signature read from `node_modules/@paypal/paypal-server-sdk/src`, one
  contract sheet (`paypal-plan.md`) written before the integration code.
- **What the plan changed in the code.** The DUPLICATE CLAIMS table is why every write is preceded by an atomic claim
  keyed on the deal and why request ids are derived from the deal, not minted per attempt. The UNKNOWN OUTCOMES table
  is why a dropped connection on capture is settled by a re-read instead of an error. The OPTIONAL FIELDS table is
  why the order request carries no field nobody asked for (there is a test for that). WHEN THE API SAYS NO became the
  single error ladder in `lib/paypal/errors.ts`.

## AI

- **The primary model is a reasoning model.** With `max_tokens` 900 it sometimes spent the whole budget thinking and
  returned `content: null` with no tool call, which silently pushed half the haggle onto the fallback model and made a
  turn take 10 seconds. Setting `reasoning_effort` ("low" for haggling, "none" for extraction and tool calls) and
  adding headroom fixed it: a turn takes 2 to 4 seconds on the primary model.
- **The fallback model always reasons first**, so it gets a larger token budget and an answer with `content: null` is
  accepted when a tool call came back.
- **Models write em dashes and curly quotes.** All model text is cleaned before it reaches the UI, and the recorder
  cleans fixtures the same way.
- **The referee caught real things.** During recording, an agent described the bike as "worn", which the listing does
  not say. The referee refused the move (INVENTED_FACT), the agent rephrased, and that refusal is now part of the
  Replay fixture's reasoning trail. A test also caught a false positive of ours: "a 6-year-old" was read as an item
  measurement.
- **Vision needed a nudge to look for flaws.** The first listing drafts missed the rusty chain. Asking the model to
  inspect metal parts, paint, fabric and tires, and to list each flaw with its location, fixed that.
- **Getting to the brief's $82 honestly.** With a $95 asking price the two agents most often met at $84. We measured
  the distribution with `scripts/video/haggle-odds.ts` and found that at a $92 asking price they meet at $82 a little
  over half the time, so the demo bike asks $92. The video and the Replay fixture are real runs that landed there.

## Next.js, tooling and the sandbox we built in

- **Next.js 16.** `next lint` is gone (ESLint CLI with the flat config), route `params` are promises, Turbopack is
  the default, and `next dev` writes an `AGENTS.md` unless `agentRules: false` is set.
- **TypeScript.** The newest TypeScript is outside typescript-eslint's supported range, so the project uses 5.9.
- **Route files may only export route handlers.** A helper exported from the webhook route had to move into `lib/`.
- **Headless video has no mouse cursor**, so the recorder injects a small cursor element. PayPal's approval window is
  a separate page with its own video file; the composer cuts to it.
- **A force push was blocked in the cloud sandbox**, so one early commit still contains a literal em dash inside a
  regular expression. The current tree has none.

## Demo video audio

- **Narrator changed to a young female voice (Jessica).** That voice had been Biscuit's, so Biscuit's five lines were
  re-rendered in a different premade voice (Lily) to keep the mascots clearly distinct from the narrator. Barley's
  lines were not touched. The earlier Biscuit files are in the git history.
- **The first cut talked over itself.** The mascot lines had been placed by counting back from the end of a scene,
  which put them on top of the narrator's last sentence and cut the final 0.1 seconds of one line. Nobody had listened
  to it. The composer now builds an audio timeline first (narrator, then each mascot line, then the cut) and fits the
  footage to it.
- **Checking audio without ears.** `scripts/video/compose.ts` now fails the build if two lines overlap, if a line runs
  into a cut, if a source file ends abruptly, if sound is still playing at a scene boundary, or if the mix peaks near
  full scale. Each line is also given a gain from its own measured peak, after widening mono to stereo at unity gain
  (the default upmix quietly costs 3 dB).
